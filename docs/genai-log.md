## How outputs were verified (evidence, not assertion)

1. **Contract validity:** `openapi-spec-validator` on the transcription.
2. **Tests executed**, not assumed: full suite against a local Postgres 16 + uvicorn service, and again
   against an "image-equivalent" run (only `app/` + `openapi/`, clean venv from `requirements.txt`,
   the Dockerfile's exact `CMD`, `PORT=10000`).
3. **Tests shown able to fail (mutation checks).** Three deliberate defects were injected into the
   service and the suite re-run; each was caught, then the code was restored and diffed byte-for-byte:
   - timestamps without an offset silently accepted as UTC → 3 failures (AC-02, AC-04);
   - framework-default 422 instead of 400 → 41 failures;
   - body validated before incident existence → 1 failure (check-order test).
4. **Static checks:** ruff (lint + format), mypy `--strict`.
5. **DB-level invariant:** direct `UPDATE`/`DELETE` via `psql` rejected by the append-only triggers.
6. **Persistence:** 100 incidents + evidence survive a service restart (`scripts/persistence_check.py`).
7. **Platform facts** used in config (Render free-tier spin-down, Postgres expiry, `RENDER_GIT_COMMIT`,
   default port 10000, Blueprint syntax) were checked against Render's documentation, not recalled.

## Agentic principles — honest assessment

- **Followed:** contract-first (transcribed spec before code); test oracles derived from Phase 2 ACs,
  not from implementation output; tests run against the HTTP interface only; mutation checks to show
  the tests have teeth; no claims without execution evidence; nothing committed, pushed, or deployed
  without approval; spec gaps surfaced instead of silently resolved.
- **Deviated / limits:** the agent wrote both the code and the tests, so they share its reading of the
  spec — independent cross-team runs are the real check. Model diagrams were produced without seeing
  the Phase 2 images. Deployment and CI-on-GitHub are unverified until a human pushes and deploys.
